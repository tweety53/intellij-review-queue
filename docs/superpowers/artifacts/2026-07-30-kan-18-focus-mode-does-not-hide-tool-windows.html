Proposal · STARTED KAN-18 2026-07-30 Review Queue · IU-2026.2

Focus mode hid a layout
nobody was looking at.

The sweep was right. The manager was right. hide() worked. It was all addressed to the wrong client session — and under a split IDE, that session has no screen.

Why

The pass starts, the diff opens, and Project and Terminal stay put

KAN-6 shipped the diagnostic that made this observable and deliberately did not fix it. Three sandbox runs produced the same result each time: the sweep enumerated 22 tool window ids, judged Terminal, Project and Database visible, and the post-hide re-check confirmed all three invisible the instant hide() returned.

The screen disagreed. Nothing in the plugin could say why.

Root cause · established from bytecode, not inferred

Two platform overrides read the current ClientId

Under a split or remote-dev IDE, the intellij.platform.backend.split module — shipped inside cwm-plugin — overrides the project-level ToolWindowManager. Two of its methods resolve the session from the ambient ClientId before doing anything:

javap -c BackendServerToolWindowManager · IU-2026.2 build 262.8665.258

// getToolWindow(id)
val session = ClientSessionsManager.getProjectSession(project, ClientId.getCurrent()) ?: return null
if (session.isLocal()) return super.getToolWindow(id)
// …otherwise the per-client window, by extractor mode

// hideToolWindow(id, …)
val session = ClientSessionsUtil.getCurrentSession(project)
if (session.isLocal()) super.hideToolWindow(id, hideSide, moveFocus, removeFromStripe, source)
updateBackendToolwindowState(id, session, { Hidden })   // ← the push that reaches a frontend

IdeLayoutController ran with no client id in scope. So it fetched the host tool windows, hid them — which flips the host WindowInfo, and is exactly why the post-hide check reported “confirmed no longer visible” — and pushed Hidden to the local session. The frontend session the reviewer is looking at was never told.

Every logged fact is consistent with this and with nothing else. This also settles the ticket’s second open question: in a plain monolith the only session is LOCAL, and the code already ran under it. The defect is specific to a split IDE.

What changes

A scoping fix, not a manager lookup

  • The sweep runs inside one session’s ClientId — chosen FRONTEND → CONTROLLER → LOCAL. Enumeration, visibility filtering, recording and hiding all happen there, so the record describes the same layout it mutates.
  • Restoring runs in every non-guest session in turn. An id is forgotten once it resolved in at least one, and kept otherwise.
  • Code With Me guests are never touched, on the way in or the way out. No built-in ClientKind expresses “non-guest”: OWNER is LOCAL ∪ CONTROLLER and excludes FRONTEND. The filter is written by hand over ClientType.
  • A re-show watch subscribes to ToolWindowManagerListener on the swept session’s own message bus and warns the first time a hidden window is shown again mid-pass.
  • Every KAN-6 log line is kept and extended to name the chosen session’s ClientId and ClientType.

No dependency change

ClientId, ClientKind, ClientType, ClientSessionsManager and ClientProjectSession are core platform (intellij.platform.core.jar, util.jar). No rdserver or cwm-plugin symbol is referenced and build.gradle.kts is untouched.

The asymmetry

Hide narrowly. Restore broadly.

This is deliberate, and it is safe in one direction only. Hiding must never touch a layout whose visibility it did not measure — that is how a union across sessions would end up hiding a window the user had closed elsewhere, then reopening it there later.

Restoring is bounded by the record: it only ever shows ids a pass already hid, so it cannot open anything the sweep did not close. That breadth is what keeps the quit-mid-pass path working when ReviewLayoutRestorer runs at post-startup, before a frontend session has attached.

Decisions

Four choices, and what ruled out the alternatives

hide-single-target-session

Which session the hide sweep acts on

Chosen
One target session, FRONTEND → CONTROLLER → LOCAL — visibility is measured in exactly the layout that is mutated, so the flat record and every existing spec scenario stay correct.
Considered
Hide in every non-guest session and record the union — a window visible in one session and closed in another gets hidden, then reopened where the user had closed it. A per-session record keyed by client id — client ids are not stable across an IDE restart, so the persisted record could not be replayed by ReviewLayoutRestorer, the one case the persistence exists for.
restore-every-non-guest-session

How restore reaches the right layout

Chosen
Restore into every non-guest session — restoring is bounded by the record, so breadth costs nothing, and it survives the frontend session not having attached yet.
Considered
Restore into the same single target session — symmetric, but at post-startup it can fall back to LOCAL, silently drop the ids from the record and leave the frontend windows hidden with nothing left to reopen them. Same target plus a retry when a session appears — most precise, but adds a listener and a retry path to a class whose safety argument rests on being simple.
clientid-recording-fixture

How the fix is covered, given the stub cannot reproduce the defect

Chosen
An injectable session-picker seam plus ClientId recording in the fixture — the exact regression becomes an assertion, in the fixture that until now could not express it.
Considered
A pure selection unit test only — leaves the wiring to the manual test guide, which would be the third bug shipped behind this gap. A fake ClientProjectSession registered with the platform — closest to production, but it extends ComponentManager, so a faithful fake is large and brittle.
reshow-watch-listener

Whether to close the known limitation in the post-hide diagnostic

Chosen
Add the deferred check as a ToolWindowManagerListener subscription on the target session, always on. Event-driven means no interval to justify and a re-show is caught whenever it happens.
Considered
One delayed re-query after a fixed interval — the interval is an unsourced guess and it observes a single instant. Both a listener and a delayed sweep — two log sources that can disagree. Gating it behind a Registry key — the next report would arrive without the evidence, the exact cycle KAN-6 shipped logging to end.

Scope beyond the ticket

The re-show watch is more than KAN-18 asks for. It was flagged as widening the change and taken deliberately; a dated line is appended to the issue under Added during implementation.

Delta specs · review-layout-management

Three added requirements

Nothing is modified or removed. A pass hides every visible tool window and Persisted state naming an unmanaged window is pruned on load both stand unchanged — they were never wrong.

A pass hides in the client session the reviewer is looking at

Exactly one session is chosen — frontend, then controlling remote client, then local — and visibility, recording and hiding all happen within it. A guest session is never chosen. An installation with only a local session behaves exactly as it did before.

  • The sweep runs in the frontend session
  • A controlling remote client is chosen when there is no frontend
  • A plain local installation is unaffected
  • A guest’s layout is never touched

Ending a pass restores into every session the reviewer could be looking at

Each recorded window is shown in every non-guest session in turn. This does not widen what is reopened. An id is forgotten once it resolved anywhere, and kept when it resolved nowhere.

  • A window hidden in one session is reopened in the session now present
  • An id that resolves nowhere stays on the record
  • A guest session is not restored into

A window re-shown during a pass is reported

Driven by the window actually being shown, not by re-checking at a chosen moment. The plugin’s own restoring is not reported — reopening the recorded windows is what ending a pass means.

  • Something reopens a hidden window mid-pass
  • Ending the pass is not reported as a re-show
  • A second pass reports independently

The only check that can see the real defect

Task 8 ends in the sandbox, because no unit test can. The handoff records which ClientType the log named — the one fact this whole change turns on.

Must not regress

Six load-bearing behaviours

  • The record is written before anything is hidden, so a part-way failure still leaves a restorable record.
  • The sweep enumerates every visible window rather than consulting a fixed id list.
  • The hide loop names the id hide() threw on and rethrows — fail-fast is unchanged.
  • The post-hide re-query still swallows its own throwable and never breaks a successful hide.
  • LEGACY_IDS pruning on loadState stays.
  • Every KAN-6 diagnostic line stays, with the pre-hide line still emitted before the mutation.
